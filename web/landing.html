No Hands: The Wispr Challenge

RESOLVE was built for the WeMakeDevs × Wispr Flow No Hands challenge: say what you want, and watch it get done and proven.

The failure it fixes

An agent can do every step right and still deliver the wrong thing.

Most automation checks that each action succeeded. Few check that the result belongs to the document, the version and the decision you actually meant.

Two files called final_report.pdf

Names collide and files get replaced. A naive agent grabs whichever matches first.

RESOLVE binds your brief and your code by stable id and SHA-256, asks when names are ambiguous, and refuses a source that changed after you chose it.

The plan changed after you approved it

You said yes to one plan. Then the instruction was revised, or the design was edited.

RESOLVE binds your approval to the exact plan digest. Any change produces a new digest, and the old approval no longer applies.

The report cites the wrong source

A generator can write a beautiful report about the wrong version of your code.

RESOLVE re-reads the stored PDF with a separate verifier. It must cite the bound brief and project hashes and every issue, or nothing is confirmed.

How it works

From one spoken goal to a verified, printable report

Intent–Entity–Effect Continuity: every result must carry an unbroken chain from your current intent revision to stable inputs, an approved plan and an output that a separate check confirms. Each link is recorded, so the chain survives restarts.

  1. 1

    Say it

    Use the in-page microphone, or dictate with Wispr Flow into the instruction box. You review the text before anything runs.

  2. 2

    Bind the inputs

    Your brief PDF and your code (the sample, or your own .zip) are pinned by id and SHA-256.

  3. 3

    Two workers, in parallel

    One reads the brief's requirements while another analyzes the code. Their recorded timestamps show the overlap.

  4. 4

    Approve the exact plan

    Issues cite file:line and the requirement they break. Edit the proposed architecture, then approve its digest.

  5. 5

    Write the report

    A composer writes the PDF with the issues, the architecture, a task graph and a test strategy.

  6. 6

    Verify independently

    A separate verifier re-reads and re-hashes the stored PDF before the mission is marked confirmed.

Honest status

What is verified, and what is not

“Verified” means real input, a real tool, an effect observed outside the code that produced it, an independent check, and an automated test that can fail.

Verified on Linux

Flagship mission

Parallel reader and analyzer, digest-bound approval, PDF output re-read and re-hashed by a separate verifier, with browser end-to-end tests.

Verified on Linux

Private accounts

Another user guessing your document, mission, project or sandbox id gets a 404 and no data. Tested against a real server in production mode.

Verified on Linux

Safe project upload

Archives are read in memory and never extracted, with path, size, zip-bomb and symlink guards. Code is parsed, never executed.

Verified on Linux

Browser fixture missions

The original CRM, reports and outbox demo, driven by Playwright (DOM-level, not physical cursor), with effects checked in each app's database.

Partly verified

Speech recognition

Audio capture, consent, validation and error handling are tested. Recognition accuracy with a real speech engine has not been verified yet.

Not run on build host

Native Windows control

Cursor movement, clicks and typing into Notepad were not exercised here: WINDOWS_NATIVE_TESTS_NOT_RUN on the build host. To test, run scripts/smoke-windows.ps1 in an interactive Windows session.

Simulated

Message delivery & connectors

The fixture outbox is SIMULATED DELIVERY; no email or message is ever sent. The connectors use built-in fixture data, with no real OAuth.

Used to build this

Wispr Flow

Wispr Flow was used while building this project, and it dictates into any RESOLVE text box like any other app. There is no Wispr SDK integration, because none is needed: RESOLVE only receives the text that appears in its fields.
